# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Code supporting a diplomski rad (thesis): **"Dizajn merenja naspram izbora modela u predviđanju realizovane volatilnosti"** — does forecast accuracy for realized volatility come more from *measurement design* choices (sampling grid, jump-robust estimator, jump test) or from *model architecture*? See `../docs/obrazlozenje-teme-diplomskog-rada.md` for the full research proposal (hypotheses H1-H5, metrics, literature). That document is the ground truth for *why* the code is structured the way it is — read it before making design changes to the measurement or evaluation layers.

The experiment is factorial: every (measurement design) x (model) combination is evaluated across horizons and market regimes, then variance in forecast loss is decomposed by ANOVA to attribute it to model choice vs. measurement choice.

## Commands

All commands run from the `Projekat/` directory using `uv` (package manager + task runner; see `pyproject.toml` / `uv.lock`).

```bash
# install / sync dependencies
uv sync

# run the full test suite
uv run pytest

# run a single test file / test
uv run pytest tests/test_jumps.py
uv run pytest tests/test_jumps.py::test_name -v

# build the measurement panel for one or more symbols
uv run python -m projekat.build_panel --symbols AAPL --start 2015-01-01 --end 2016-01-01 --grids 5m --estimators bpv --jump-tests bns
```

`main.py` (`uv run python src/main.py`) just prints the `LSE_KEY` env var — a smoke test for `.env` loading, not an entry point for the pipeline.

Tests (`tests/`) use synthetic, seeded fixtures (`tests/conftest.py`) with **no network access** — they never hit the vault or FRED.

## Data source & credentials

Intraday 1-minute bars come from the **LSE vault** (`lse-data` package) via `projekat.data.vault.fetch_1m`, authenticated with `LSE_KEY` in `.env` (loaded via `python-dotenv`). Downloads are cached under `data/raw/1m/` as Parquet with a JSON provenance manifest (hash, row count, fetch time) per file; re-fetching is a no-op unless `force=True`. `data/` is gitignored — entirely regenerable from the vault + FRED (VIX).

## Architecture

The pipeline is two sequential layers with a **frozen schema contract** between them (`measure/schema.py`, `PANEL_SCHEMA`) — treat that file as an API boundary, not an implementation detail.

```
data/  →  measure/  →  (panel parquet)  →  model/  →  evaluation/  →  results/
```

### 1. Measurement layer (`measure/`, orchestrated by `build_panel.py`)

Per symbol: fetch 1m bars (`data/vault.py`) → clean/filter each day against the real exchange calendar (`data/clean.py`, `data/calendar.py`) → resample to a grid and compute log-returns (`measure/grids.py`) → compute realized measures and jump decomposition per day (`measure/panel.py`) → roll HAR aggregates (`measure/rolling.py`) → validate against the schema (`measure/schema.py`) → write `data/processed/*.parquet`.

**`MeasurementDesign`** (`measure/design.py`) is the experiment's design space as a first-class, hashable object: `(grid, estimator, jump_test, threshold)` → `design_id` (e.g. `5m__bpv__bns`), which becomes the ANOVA factor key downstream (`evaluation/anova.py:parse_design_id` is the exact inverse of `MeasurementDesign.id`, relying on its fixed field order — never split `design_id` ad hoc elsewhere).

**Registry pattern (critical, applies to both `measure/` and `model/`):** `measure/panel.py` resolves A2 estimators and A3 jump tests **by name only** from `measure/registry.py`'s `ESTIMATORS`/`JUMP_TESTS` dicts — it must never import a concrete estimator/jump-test module. Modules under `measure/estimators/` and `measure/jumps/` self-register via `@register_estimator` / `@register_jump_test` decorators on import. **Adding a new estimator or jump test = one new file with the decorator, zero edits to `panel.py` or the registry.** The same pattern applies in `model/`: `model/runner.py` resolves models by name from `model/registry.py`'s `MODELS` dict; `model/baselines/`, `model/econometric/`, `model/trees/`, `model/sequence/` submodules self-register via `@register_model`.

Three experimental factors, all pinned in `config.py` with the reasoning for each fixed choice documented inline there (read it before touching any of these):
- **A1 — sampling grid**: `1m` / `5m` / `15m` (`GRIDS`). Not `10m` — no native 10m timeframe in the vault.
- **A2 — jump-robust estimator**: `bpv`, `medrv`, `trbpv` (`measure/estimators/`), selected via `ESTIMATORS`.
- **A3 — jump test**: `naive`, `bns`, `lm`, `lm_fdr` (`measure/jumps/`), selected via `JUMP_TESTS`. `lm` and `lm_fdr` need whole-history context (trailing K-window for the Lee-Mykland statistic, trailing W-day window for Benjamini-Hochberg FDR) computed up front in `panel.py::_lm_day_stats`, which now also returns the per-day `local_sigma` slice so `panel.py` can call `JUMP_TESTS["lm"]`/`JUMP_TESTS["lm_fdr"]` directly instead of hand-building a `JumpVerdict`, unlike `naive`/`bns` which are purely per-day. `naive`'s sigma comes from the `robust` (jump-robust) estimator passed in, never from `np.std(r)` over the whole day — the latter would include the tested jump in its own denominator.

Non-obvious invariants worth knowing before editing this layer:
- The `MIN_INTRADAY_OBS` floor is enforced **once, grid-wide**, in `data/clean.py::has_sufficient_coverage` — never per-estimator inside `panel.py`. Applying it per estimator would leave e.g. `bpv` designs with more usable days than `medrv`/`trbpv` designs at the same grid, an unbalanced factorial design that corrupts ANOVA variance shares. (`qa/checks.py::assert_min_intraday_obs` is a regression guard for this, not a live filter.)
- `LM_LOCAL_WINDOW_K` is held fixed at **4 trading sessions** across all grids (not a literature-matched constant) specifically so only sampling frequency varies with A1, not local-window length too.
- Session windows come from the real NYSE calendar (`exchange_calendars`, `data/calendar.py`), not a fixed UTC clock window — a fixed window leaks thin post-close bars into early-close sessions.
- `RS_pos + RS_neg == RV_d` is a genuine hard-asserted invariant (`qa/checks.py`); `C_d + J_d == RV_d` is not (it holds by construction and asserts nothing).
- Overnight returns are never included in RV — each day's return array is built purely from that day's own prices (see `build_panel.py::_concat_returns_in_order`).

### 2. Modelling layer (`model/`, orchestrated by `model/runner.py`)

Reads the panel and, per model, fits/predicts across an **anchored walk-forward** validation scheme (`model/windows.py`): training start fixed at 2010-01-01, only the training end expands, 11 windows over 2010-2025 (never rolling — eliminates lookahead). Each window's training data further carves out its last year as a validation fold (`split_with_validation`), used **only** to estimate the Jensen back-transform correction from out-of-fold residuals and (as of this session) Mincer-Zarnowitz coefficients — never for hyperparameter tuning or evaluation.

The Jensen back-transform correction (`model/backtransform.py`) is **non-parametric**: `a = ln(mean(exp(residual)))` on out-of-fold validation residuals, applied as `y_hat = exp(log_y_hat + a)` — not the Gaussian `0.5*sigma^2` formula (which assumes normally-distributed log residuals; RV residuals need not be). Every `FittedModel` exposes this as `backtransform_correction` (not `sigma2`), computed by `backtransform.py::residual_correction`. `runner.py::run_all` now returns `(test_results, val_results)` — a tuple, not a single frame — where `val_results` carries the same per-row shape (including `window_id`, `log_y_hat`, `backtransform_correction`) for the validation fold of each window, used only by `results/tables.py::attach_mz_recalibration` to fit Mincer-Zarnowitz per `(model, design_id, horizon, window_id)` cell and recalibrate test predictions; `main_result_table` reports `qlike` and `qlike_recalibrated` side by side when that column is present, never one replacing the other.

Models implement the `Model`/`FittedModel` protocols (`model/protocols.py`) and declare `depends_on: frozenset[str]` — the subset of `{"grid", "estimator", "jump_test"}` their inputs actually depend on. `runner.py::_representative_designs` uses this to fit a model once per distinct combination of only the factors it depends on (e.g. a grid-only model fits 3x, not up to 36x) — both for compute and so duplicated non-independent rows don't corrupt the ANOVA.

Models: `naive`, `har`, `log_har`, `har_j`, `char`, `shar`, `harq`, `har_iv`, `arfima`, `mem` (econometric, `model/econometric/`), `lightgbm`/`xgboost` (`model/trees/`), `patchtst` (`model/sequence/`, the one stochastic model — 5 seeds, `STOCHASTIC_SEEDS`). Every model declares `is_sequence_model: bool` on the `Model` protocol; `runner.py::run_one` dispatches to `_run_sequence_model` (sequence-building via `build_sequences`/`targets_for_sequences` instead of a flat feature matrix) based on that flag, not on `model_name == "patchtst"` — a future second sequence model only needs `is_sequence_model = True`, no edit to `runner.py`.

**Three deliberately distinct positivity mechanisms**, never unified:
- **Log + non-parametric back-transform correction** (`log_har`, `shar`, `harq`, `har_iv`, `char`, `har_j`, `arfima`, plus the tree/sequence models, all sharing `_ols_base.py::fit_ols` where applicable): fit in log space, back-transformed via `backtransform.py`. This is the majority mechanism.
- **NNLS directly on levels** (`har.py`, the plain "HAR" model — NOT `log_har`): non-negative least squares with non-negative regressors (`RV_d/w/m`, already variances) guarantees a non-negative forecast by construction, so there is no log transform and no back-transform correction at all.
- **Structural positivity from a multiplicative functional form** (`mem.py`, exponential-QML Multiplicative Error Model): the conditional-mean recursion `mu_t = omega + alpha*RV_{t-1} + beta*mu_{t-1}` is a convex combination of non-negative terms, so `mu_t >= 0` by construction whenever the fitted parameters satisfy their box/stationarity constraints — again no log transform, no correction.

Models using the second and third mechanisms declare `predicts_levels: bool = True` on the `Model` protocol; `runner.py::run_one`/`_run_sequence_model` check this flag and skip `backtransform()` entirely for such models (their `predict()` already returns `y_{t,h}` in levels), writing `NaN` into the `log_y_hat`/`backtransform_correction` output columns rather than a value that would be misleading if read as log-space. **`har` (NNLS, levels) and `log_har` (log+correction) are two separate, permanently distinct models** — a natural-seeming "just use one HAR" simplification would erase the ability to compare whether the positivity mechanism itself, not just the feature set, affects forecast accuracy. `log_har` — not `har` — is the headline benchmark for `evaluation/losses.py::relative_qlike`.

**Foundation models (`model/foundation/`)**: `ttm_rv` (grid), `ttm_c` / `ttm_c_plus_j` (grid, estimator, jump_test), and the `log_har_ttm` hybrid (grid). All are **zero-shot, deterministic, never trained** — `fit()` exists only to satisfy the `Model` protocol and to estimate the back-transform correction; the checkpoint weights are never touched (`stochastic = False`, no seeds). The checkpoint is **pinned exactly** in `config.py` (`TTM_MODEL_ID` + `TTM_REVISION`, currently the `512-192-r2` branch), never "TTM" generically — different releases have different pretraining datasets, so a contamination check against an unpinned model would prove nothing. A non-`ft` branch is pinned deliberately: the frequency-prefix-tuned variants require a `freq_token` input, which would add an unjustified hyperparameter to a zero-shot path.

The **pretraining contamination check** (`model/foundation/contamination.py`) is a first-class recorded artefact: it compares the pinned checkpoint's published cutoff (`config.TTM_PRETRAIN_CUTOFF`) against the test period and writes `results/ttm_contamination_check.json` **either way**, clean or not. `runner.py::run_all` runs it before producing any `ttm_*`/`log_har_ttm` forecast — no such number is reported without the artefact. When contamination is found, the overlap is quantified and the model is **kept in the analysis, labelled contaminated** — never silently dropped and never silently treated as clean.

`ttm_c_plus_j` and `log_har_ttm` both take **one correction estimated on the combined forecast**, never one per component: `a = ln(mean(exp(residual)))` is QLIKE-optimal only for the series it was estimated on, so correcting `C` and `J` separately and then summing would leave the RV forecast with no controlled bias at all. `backtransform.py` exposes this as `combined_forecast_correction`/`apply_combined_correction` (a multiplicative factor on the already-summed levels forecast) so no model can get it wrong locally. `log_har_ttm` combines **in log space, before the correction**, with weights **fixed at 0.5/0.5 and never optimized** — not on the validation fold, not anywhere (same reasoning as WI-5's pinned LightGBM hyperparameters: an optimized combination would make the hybrid's variance contribution reflect search effort rather than architecture, and the validation fold is already committed to the correction and Mincer-Zarnowitz coefficients). Weighting in levels would be a different estimator and must not be substituted. Expect `ttm_j` to predict near zero throughout — that is a measurement supporting the CHAR rationale, not a bug to fix.

`arfima` (local-Whittle `d` per symbol, then ARMA(p,q) selected by BIC over `{0,1,2}^2` on the fractionally-differenced series, `statsmodels.tsa.arima.model.ARIMA` with `d=0`) and `mem` are both fit **independently per symbol** — unlike the cross-sectional HAR family, a univariate long-memory/GARCH-style time-series model cannot be pooled across symbols. Both declare `depends_on = {"grid"}` (their inputs are RV_d alone, identical under every A2/A3 combination at a given grid).

Targets (`model/targets.py`): `y_{t,h}` is the **h-day average** future RV (Corsi's own HAR construction), modelled in `log()` — **with one documented exception: the jump component `J`, which is forecast in levels.** `J == 0` on most days (the conditional decomposition sets `J = 0` whenever the jump test is not significant), so `log(J)` is undefined and a uniform log rule would either crash or silently forecast the log of an arbitrary epsilon. `model/foundation/ttm_c_plus_j.py` therefore forecasts `C` on the normal log path and `J` in levels, clips each at zero, and sums **in levels**. The precise invariant is "targets are modelled in log, uniformly, except the jump component, which is in levels because `J = 0` is a legitimate and frequent value" — anything reading the older unqualified wording should treat this paragraph as the correction. Forecasts are back-transformed with a shared Jensen-inequality correction (`model/backtransform.py`) — never a per-model ad hoc `exp()`. `add_target` and `model/features.py::build_sequences`/`model/sequence/patchtst.py::_targets_for_sequences` all group/sort by `symbol` before shifting or windowing — `design_df`/`test_df` span every symbol in the universe (filtered only by date range in `windows.py`), so shifting or building a rolling window on a frame sorted by date alone would silently pull a "future" RV or a sequence window from a different symbol at any boundary where two symbols' date ranges interleave.

Seed handling for stochastic models (`runner.py::collapse_seeds` / `ensemble_forecast`): the **primary** reported figure averages per-seed **losses**, not forecasts. A seed-averaged-forecast ensemble exists as an explicitly separate, secondary figure and must never replace the primary one. `ensemble_forecast` averages the raw `log_y_hat` (pre-back-transform prediction) and each seed's `backtransform_correction` separately across seeds, then calls `backtransform()` exactly once on the two means — never `np.log(y_hat)` on the already-back-transformed per-seed forecast, which would bake each seed's own correction back in before averaging and double-count it.

### 3. Evaluation layer (`evaluation/`)

Four levels, matching the thesis's metric structure:
- **Level 1 — accuracy**: `evaluation/losses.py` — QLIKE (primary, robust to noisy RV proxy per Patton 2011), RMSE/MAE (secondary), relative QLIKE. **Relative QLIKE is a ratio of means, never a mean of ratios**: `mean(QLIKE_model) / mean(QLIKE_log_har)` over the pooled test period. The two are not interchangeable — a mean of ratios blows up whenever a single day's benchmark loss approaches zero, which happens. The baseline is `log_har` (`RELATIVE_QLIKE_BASELINE`), not `har`. QLIKE wins on disagreement with MAE, but a reversal is flagged only when **Diebold-Mariano significant at α=0.05 on both metrics** — flagging every mean-level reversal would report rounding noise as disagreement. Use `ranking_disagreement_table(daily_losses)` on the per-day frame, computed per `(horizon, design_id)` cell; `main_result_table` no longer carries this flag because it is already aggregated and cannot compute DM significance. `mae_median_variant` (correction `a = 0`) is the required robustness partner for MAE, since QLIKE/RMSE are optimized by the conditional mean and MAE by the conditional median.
- **Level 2 — significance & decomposition**: `evaluation/dm_test.py` (Diebold-Mariano — pass the actual forecast `h` through any caller; the HAC lag count depends on it. With 24 designs × ~14 models, exhaustive pairwise DM is thousands of tests, so every reported family goes through **Benjamini-Hochberg FDR control** via `benjamini_hochberg_dm(..., family=...)` — BH is already this repo's convention in `measure/jumps/lm_fdr.py`. The family must be named explicitly and is recorded in the output's `dm_family` column; `DM_FAMILIES` declares the valid ones, and `dm_against_baseline` implements the pre-declared "every model vs `log_har`" contrast set), `evaluation/mcs.py` (Model Confidence Set — membership is **not** a ranking of point losses; `model_confidence_set(..., horizon=...)` forwards `horizon` to `diebold_mariano` as `h`, since defaulting to `h=1` under-corrects the HAC variance at `h=5`/`h=22`), `evaluation/mincer_zarnowitz.py` (regression of realized value on forecast, intercept=0/slope=1 test; wired into `results/tables.py::attach_mz_recalibration`, which fits it per `(model, design_id, horizon, window_id)` cell **from the validation fold only** and reports raw and recalibrated QLIKE side by side — recalibrating before the primary metric would be lookahead).

  **`evaluation/anova.py` is the thesis's headline result.** The dependent variable is the **daily** QLIKE loss, one row per (model, design, horizon, symbol, day) — cell means would leave no error term. Non-obvious requirements, all enforced in code and explained at length in the module docstring:
  - **Fitted separately per horizon, never pooled.** `decompose_variance_*` return `{horizon: ANOVATable}`. Horizon is in the row key but is deliberately *not* a factor: h=1/5/22 have different target scales, so pooling dumps explainable variance into the error term and deflates every partial eta-squared — including the measurement share the thesis exists to report.
  - **`symbol` is an explicit blocking factor**, for the same reason: left in the residual it inflates the error term and shrinks all reported shares.
  - **Type III SS with sum-to-zero contrasts, asserted not assumed.** The design is unbalanced by construction (grid-only models get duplicated rows across the 12 estimator × jump_test combinations) and carries three deliberate interactions, so Type II and Type III disagree on main effects. Type III is undefined without sum-to-zero coding, so the contrasts are written into the formula (`C(x, Sum)`) rather than left to patsy's Treatment default.
  - **Partial eta-squared is reported as a descriptive variance share.** Designs derive from the same raw 1m bars, so 1m and 5m RV for the same day are highly correlated and the F-test's independence assumption does not hold. Any reported F/p must be read against **two-way (day × symbol) cluster-robust SEs** (Cameron-Gelbach-Miller, both dimensions simultaneously — not two one-way options), returned in `ANOVATable.clustered`. `block_bootstrap_variance_shares` is the optional alternative inference path, with **block length = h**, matching `mcs.py`'s convention so the two paths cannot disagree by construction.
  - **Skewness robustness is required, not optional.** `robustness_table` runs the same decomposition four ways side by side — raw daily QLIKE (primary), `log(QLIKE)`, within-day ranks across models, and raw with the top 1% of loss days dropped (the direct answer to "would this hold without March 2020?"). Stable shares across all four is a strong robustness claim; instability must be visible *before* the text is written, which is why this is a first-class table and not a buried diagnostic.
  - The two decompositions are returned **separately and never aggregated** into one headline number — that remains an open question with the advisor. `aggregate_headline_share` exists as a clearly marked hook that raises `NotImplementedError` so the decision has one obvious implementation site.
  - Interaction terms `grid:estimator`, `grid:jump_test`, `model:jump_test` are **structural, not incidental** — microstructure noise makes `RV - BPV` shift systematically with A1. Read the module docstring before touching them.
- **Level 3 — economic evaluation (VaR)**: `evaluation/var.py` — Kupiec, Christoffersen, Dynamic Quantile tests, Lopez loss. Breaches are measured against `r_d` (open-to-close), never a close-to-close return series, since RV is built purely from intraday returns and excludes the overnight gap; using close-to-close would systematically understate VaR risk and make Kupiec reject on a units mismatch rather than a real finding. VaR backtests pool all 11 test windows together (~2,772 days) rather than testing per-window, since a single 252-day window gives Kupiec essentially no power (~2.5 expected breaches at the 1% level).
- **Level 4 — jump-detection characterization**: `qa/checks.py` (Jaccard overlap between jump-test variants, jump-day share, placebo-test support for H5). No classification metrics (precision/recall) — there is no ground truth for what a "real" jump is. QLIKE is undefined at `J_d == 0` (division by zero/log of zero) — never apply `losses.py::qlike` to the jump component series; it is only ever computed on `(y_true, y_hat)`, the RV forecast, throughout the codebase. `assert_semivariance_identity` and `assert_min_intraday_obs` now actually run against the real built panel in `build_panel.py::main`, not just in tests; `corporate.verify_split_adjustment` similarly runs once per symbol in `build_panel_for_symbol` (non-fatal if the corporate-actions fetch itself fails, but a real `UnadjustedDataError` propagates and stops the build).

`evaluation/stratify.py` splits results by regime (calm/turbulent, by `RV_m` quantile), jump-day presence, and horizon — averaging across the whole sample can hide a model winning in calm periods and losing in turbulent ones, which matters specifically for risk management. The regime boundary (`compute_and_persist_regime_boundary`) is computed **once**, from window 1's training data only, and persisted to `data/processed/regime_boundary.json` — `tag_regime` always loads that fixed value, never recomputes it from whichever window's data is in scope, since letting the boundary shift per window would make a given calendar day's regime label ambiguous (it would depend on which window produced the forecast being tagged).

## Conventions to preserve

- **Never bypass the registries.** `measure/panel.py` and `model/runner.py` must resolve estimators/jump-tests/models by string name only; a new implementation is always "one new file with a decorator," never an edit to the resolver.
- **`measure/schema.py` (`PANEL_SCHEMA`) is the frozen contract** between the measurement and modelling layers — column names, dtypes, and units are fixed there. Treat a change to it as a breaking change requiring updates on both sides of the boundary.
- Fixed design constants in `config.py` (grids, K, W, TrBPV threshold, QA thresholds) carry inline rationale for *why* each was pinned rather than made variable — read the comment before changing a value, since several were pinned specifically to keep the factorial design balanced for ANOVA.
- Hard assertions vs. counted diagnostics in `qa/checks.py` are a deliberate split (see its module docstring) — a new QA check should default to a diagnostic unless it can never legitimately fire on real data.

## Changelog: correctness fixes (2026-09-14)

A multi-angle code review surfaced the following bugs, all now fixed and covered by `uv run pytest` (24 passed):

1. **Cross-symbol contamination in targets/sequences** — `model/targets.py::add_target`, `model/features.py::build_sequences`, and `model/sequence/patchtst.py::_targets_for_sequences` sorted by `date` only; on the multi-symbol `design_df`/`test_df` passed by `runner.py`, this let a horizon-ahead shift or a 60-day sequence window silently cross from one symbol into another at date boundaries. Fixed by sorting/grouping by `symbol` first everywhere the three functions touch a multi-symbol frame; `build_sequences` also now rejects any window whose first and last row don't share a symbol.
2. **`measure/jumps/naive.py` self-contaminated sigma** — the naive jump test estimated its own denominator via `np.std(r)` over the whole day, which includes the very jump being tested, letting a large enough jump inflate its own threshold and escape detection. Fixed to derive sigma from the jump-robust `robust` estimator (already excludes the jump by construction) instead: `sigma = sqrt(robust)`.
3. **`measure/panel.py` bypassed the `lm`/`lm_fdr` registry entries** — `build_symbol_design` hand-built `JumpVerdict` objects and called `_gumbel.critical_value` directly instead of dispatching through `JUMP_TESTS["lm"]`/`JUMP_TESTS["lm_fdr"]`, duplicating logic that could silently drift from the registered functions. Fixed: `_lm_day_stats` now also returns the per-day `local_sigma` slice it already computes, and `build_symbol_design` calls `JUMP_TESTS["lm"](r, rv, robust, local_sigma=...)` / `JUMP_TESTS["lm_fdr"](..., precomputed=...)` directly. (The `local_sigma_series`/`DayStat`/`lm_fdr_significance_series` imports at the top of `panel.py` remain — computing the trailing K/W-window statistics genuinely needs whole-history context the per-day `JumpTest` protocol can't express, which is the documented, intentional exception, not a further violation.)
4. **`evaluation/mcs.py::model_confidence_set` ignored forecast horizon** — always called `diebold_mariano` with the default `h=1`, under-correcting the HAC variance at `h=5`/`h=22` where overlapping targets (`targets.py`) induce real autocorrelation. Fixed: `model_confidence_set` takes a `horizon` parameter and forwards it as `h`; `results/tables.py::mcs_membership_table` passes its per-cell `horizon` through.
5. **`evaluation/losses.py::ranking_disagreement` was dead code** — defined but never called, so a real QLIKE-vs-MAE ranking disagreement was silently absent from output instead of flagged. Fixed: `results/tables.py::main_result_table` now computes a `ranking_disagreement` column per `(design_id, horizon, regime, jump_day)` cell.
6. **`data/corporate.py::verify_split_adjustment` (the split-adjustment hard gate) was never called** in production, only in tests. Fixed: `build_panel.py::build_panel_for_symbol` now calls `fetch_corporate_actions` + `verify_split_adjustment` once per symbol; a real `UnadjustedDataError` propagates and stops the build, while a corporate-actions *fetch* failure (network/vendor) only warns and skips the gate for that symbol.
7. **`qa/checks.py` hard assertions were never invoked against the real built panel** — only exercised in tests. Fixed: `build_panel.py::main` now calls `assert_semivariance_identity` and `assert_min_intraday_obs` on the full assembled panel before writing parquet. `assert_no_split_date_unadjusted` was simplified to a no-arg audit-trail marker (it never inspected its former arguments — the real check is `corporate.verify_split_adjustment`).
8. **`.gitignore`'s bare `data/` pattern** matched at any depth, silently also ignoring `src/projekat/data/` (the real source package: `calendar.py`, `clean.py`, `corporate.py`, `vault.py`, `vix.py`), not just the intended repo-root cache directory. Fixed by anchoring it to `/data/`.
9. **`model/runner.py::run_one` dispatched to the sequence-model path via `model_name == "patchtst"`** instead of a protocol-level capability. Fixed: added `is_sequence_model: bool` to the `Model` protocol (`model/protocols.py`), set on every concrete model; `run_one` now checks `model.is_sequence_model`.
10. **`tests/test_gumbel.py` was stale** — it asserted the module's own superseded Revision-8 behavior (a `SIMULATED_CRITICAL_VALUES` table that was never implemented, per `_gumbel.py`'s Revision-9 docstring explaining why that comparison was flawed), causing `ImportError` at collection and aborting the entire test run. ## Changelog: non-parametric back-transform + Mincer-Zarnowitz wiring (2026-09-14, later same day)

A second review pass against a stated invariant list (anchored walk-forward, validation-fold usage, back-transform formula, `depends_on`, direct point-in-time targets, seed ensembling, VaR/regime/QLIKE conventions) confirmed most invariants already held (anchored windows, `depends_on` on every model, VaR breaches against `r_d`, pooled VaR backtests, fixed regime boundary from window 1, QLIKE never applied to the jump series). Two real gaps were found and fixed:

1. **Back-transform correction used the Gaussian `0.5*sigma^2` formula instead of the required non-parametric `a = ln(mean(exp(residual)))`.** The Gaussian formula assumes log-residuals are normally distributed; RV residuals need not be, and using it systematically mis-corrects whenever the residual distribution is skewed or fat-tailed. Fixed: `model/backtransform.py::residual_correction` (renamed from `residual_variance`) now computes the non-parametric correction directly from out-of-fold validation residuals; `backtransform()` takes an additive `correction` term instead of `sigma2`. Every `FittedModel` implementer (`naive`, the OLS-family `_ols_base.py`, `lightgbm_model.py`, `xgboost_model.py`, `patchtst.py`) was updated to expose `backtransform_correction` instead of `sigma2`, computed the same way. Behavior for perfectly Gaussian residuals is nearly identical to the old formula (both estimate `E[exp(residual)]`); the difference only matters — and matters most — exactly where the module's own docstring says tree/sequence models produce non-Gaussian residuals.
2. **`ensemble_forecast`'s secondary seed-ensemble figure averaged `np.log(y_hat)`** — i.e., the log of the *already back-transformed* per-seed forecast, which equals `log_y_hat + backtransform_correction` and therefore baked each seed's own correction back in before averaging, double-counting it relative to a clean log-space average. Fixed: `run_one`/`_run_sequence_model` now also emit the raw `log_y_hat` and `backtransform_correction` columns; `ensemble_forecast` averages `log_y_hat` and `backtransform_correction` separately across seeds and calls `backtransform()` exactly once on the two means, matching the invariant that ensemble averaging happens "in log space, before back-transformation."
3. **Mincer-Zarnowitz (`evaluation/mincer_zarnowitz.py`) existed but had no caller anywhere** — the invariant that it be "a parallel secondary figure, coefficients from the validation fold only" was unmet because nothing computed those coefficients or attached a recalibrated QLIKE. Fixed by adding validation-fold plumbing: `runner.py::run_one`/`_run_sequence_model` now return `(test_rows, val_rows)` instead of a single frame (both carry a new `window_id` tag), and `run_all` returns `(test_results, val_results)`. `results/tables.py::attach_mz_recalibration(test_results, val_results)` fits MZ per `(model, design_id, horizon, window_id)` cell from `val_results` only, recalibrates test predictions (`y_hat_recalibrated = intercept + slope * y_hat`), and attaches `qlike_recalibrated` alongside the raw `qlike` column — `main_result_table` reports both side by side when present, never substituting one for the other. This is a signature-breaking change to `run_all`/`run_one` (tuple return instead of a single DataFrame); no other code in the repo called them yet, so nothing else needed updating.

## Changelog: WI-3/WI-4 econometric models — NNLS `har`/`log_har` split, `arfima`, `mem` (2026-09-15)

WI-3 (econometric models) and WI-5/WI-6 (LightGBM, PatchTST) were mostly already implemented from earlier sessions. One real gap in WI-3: the existing `har.py` was actually what the spec calls `log_har` (OLS in log space via `_ols_base.py::fit_ols`, back-transformed) — there was no separate NNLS-in-levels `har` and no `log_har` at all, so the "three deliberately distinct positivity mechanisms" requirement was unmet (only one of the three existed). WI-4 (`arfima`, `mem`) was entirely missing. Fixed:

1. **Split `har`/`log_har` into two permanently separate models.** The prior `har.py` (log+correction OLS) was renamed to `model/econometric/log_har.py`, registered as `"log_har"` — now explicitly documented as the headline benchmark for `relative_qlike`. A new `model/econometric/har.py` was built from scratch: NNLS (`scipy.optimize.nnls`) fit directly on **level** targets (`model/targets.py::LEVEL_TARGET_COL`, a new column added alongside the existing log `TARGET_COL`) over non-negative regressors (`RV_d/w/m`, already variances), guaranteeing a non-negative forecast by construction with no log transform and no back-transform correction.
2. **Added a `predicts_levels: bool` flag to the `Model`/`FittedModel` protocols** (`model/protocols.py`) for models whose positivity is structural rather than log+correction-based. `runner.py::run_one`/`_run_sequence_model` check this flag and skip `backtransform()` entirely for such models (their `predict()` already returns levels), writing `NaN` into the `log_y_hat`/`backtransform_correction` output columns rather than a value that would be misleading if read as log-space. Every existing model was updated to declare `predicts_levels = False` explicitly.
3. **Built `model/econometric/arfima.py` and `model/econometric/mem.py`** (WI-4), both `depends_on = {"grid"}`, both fit **independently per symbol** (unlike the cross-sectional HAR family) since a univariate long-memory/GARCH-style time series model can't be pooled across symbols:
   - `arfima`: local-Whittle estimate of the fractional-differencing parameter `d` (coarse grid search over the low-frequency periodogram), fractional differencing via the truncated binomial-series expansion of `(1-L)^d`, then `(p,q)` selected by BIC over `{0,1,2}^2` on the differenced series (`statsmodels.tsa.arima.model.ARIMA` with `d=0`). Forecasts are re-integrated back to levels via the inverse `(1-L)^-d` weights convolved against the training tail plus the forecast path — **not** anchored at "last level + a local delta" (an earlier draft of this that used that shortcut was numerically wrong by ~10 log-units on a smoke test, since `(1-L)^-d` is a long-memory operator whose reconstruction depends on the full differenced history, not just the most recent value).
   - `mem`: exponential-QML Multiplicative Error Model (Engle 2002), `mu_t = omega + alpha*RV_{t-1} + beta*mu_{t-1}`, fit by maximizing the exponential log-likelihood subject to `omega > 0, alpha >= 0, beta >= 0, alpha+beta < 1` (`scipy.optimize.minimize`, L-BFGS-B). Positivity is structural (a convex combination of non-negative terms), so `predicts_levels = True` and no correction is computed.
4. Updated stale docstrings: `evaluation/anova.py::decompose_variance_grid_only` now lists the correct current grid-only model set; `evaluation/losses.py::relative_qlike` now explicitly says the QLIKE baseline is `log_har`, not `har`.
5. Added `tests/test_runner.py`: every registered model (13 total) round-trips through `run_all` by name alone; `har`'s NNLS forecast is never negative and carries no back-transform correction; `log_har` does carry one; `collapse_seeds` is verified to be a true no-op (`assert_frame_equal` against the input) while `ensemble_forecast` collapses multiple seed rows into one and produces a different value than naively averaging the already-back-transformed forecasts — the two paths are structurally distinct (different output row counts) as WI-6 required, not just differently-valued.

Wall-clock check for WI-6 (PatchTST, as required before any further change to it): a single fit on a small synthetic panel took ~5.7s; scaling to the real grid (5 seeds x ~24 designs x 3 horizons x 11 windows ≈ 3,960 fits, with training-set size growing per window) was estimated at roughly 22-66 hours of sequential CPU wall-clock time. Left as-is per instruction — this is a compute-budget decision for whoever runs the full pipeline, not something to silently reduce in code.
